# Bounded Product UX Exploration

Use this guide from Product, PRD or FRS work only when a user journey, navigation, interaction, usability or accessibility decision is needed to clarify requirements. It supplements the current requirements standard; it does not replace its source/readiness gates or require another agent. Pure scope, business-rule, backend or document-format work does not need a UX search. For SRS work, consume accepted UX outcomes as relevant system constraints rather than redesigning the interface.

## Inputs and output

Identify the user goal, feature/journey IDs, available user evidence, product/brand/platform constraints, source owners/versions and existing accepted UX artifacts. Preserve unresolved inputs explicitly. Return conceptual flows/navigation/interaction options or requested low-detail wireframes, the affected requirement/acceptance IDs, rationale and query/source evidence, proposal/acceptance status, acceptance basis and remaining owner questions. Use the existing requirements artifact or its referenced assets; a separate UX report or design-system master is not required.

## Conditional workflow

1. **Confirm need and reuse.** State the requirement question that depends on UX. Read accepted journeys, wireframes, brand/design-system sources and earlier decisions first. If they answer it, reuse them; document gaps rather than regenerate visual direction.
2. **Load the installed skill when needed.** Resolve `ui-ux-pro-max/SKILL.md` through the runtime catalog, read its instructions and use its search script by absolute path relative to the installed directory. Do not assume a repository-local script, plugin environment variable or implementation stack. If unavailable, report the limitation; continue independent requirements work from existing evidence. Block only dependent readiness when a material UX question remains unresolved, not the entire document merely because the optional tool is absent. Do not install it implicitly or claim searches ran.
3. **Explore the smallest relevant question.** Use a focused explicit domain for the user outcome, navigation or interaction question. Use `--design-system` only when the requested scope actually includes coherent new page/product visual direction; treat its detailed styling as proposals for the later design owner. Follow the skill's query verification, one-retry/fallback, privacy and RTL rules. Stack guidance is unnecessary for most Product work; use it only for a relevant confirmed stack, never choose one as a side effect. Avoid private project data in queries.
4. **Translate examples into requirements.** Assess fit against the user goal, source evidence and constraints. Distinguish guidance from observed user research. Record proposed behavior separately from choices already accepted within existing authority; do not invent consensus, usability findings or compliance. Express accepted outcomes as observable PRD/FRS behavior and acceptance criteria. Return material product/brand questions to their owner; do not require a new approval ceremony for choices already authorized. Keep detailed technical/component design with Frontend Experience.
5. **Hand off the same decisions.** Record stable requirement/journey IDs, UX artifact references/version, proposal versus accepted status, acceptance basis, alternatives and unresolved detail for the normal System Analysis/System Design handoff. Frontend Experience reuses accepted choices and refines gaps. Later findings return material behavior changes to Product instead of silently overriding them. Independent workflow invocation remains unchanged.

## Boundaries

Do not author production UI, choose architecture/frameworks, invent API capabilities or maintain a second design-system authority during Product exploration. Preserve supplied approved visual constraints, while detailed palettes, typography/tokens, responsive layouts and component specifications belong to Frontend Experience. Do not persist a master/page override merely to complete requirements; if such persistence is explicitly in scope, follow the installed skill's verified-output and existing-file rules, including explicit authorization before `--force`.

Completion means the scoped requirement question is resolved with traceable accepted behavior, or clearly reported as open with owner/next action. A completed proposal can be handed back for a decision; it is not automatically a ready requirement, approved design or tested user experience.
